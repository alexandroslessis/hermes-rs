### What it does
1. **Folders and threads.** Projects are collapsible headers (32 px: colour monogram, name, a status dot and the count while closed, chevron; the folder path in a tooltip; a new-thread button on hover). Threads are 36 px rows under them, newest first, eight per folder then "Show N more". User projects first (by newest thread), automatic git-repository projects, then "No project" last. A project with no thread says so. Closed folders are remembered.
2. **Rows.** Title (end-truncated since the review, as t3code's; on one line), relative time (`now`, `5m`, `3h`, `2d`), status in the same slot: working (spinner icon), approval (shield, warning colour), failed, unread (t3code's "Done"). Hover shows rename, archive and delete over the right edge; right click opens a Kit context menu (Rename, Pin/Unpin, Archive, Move to project submenu, Copy thread ID, Delete); double click renames in place. Keys (sidebar focused): Up/Down/Home/End move a cursor ring, Enter opens a thread or toggles a folder, Left/Right close/open a folder, F2 renames, Delete asks to delete. Delete (key, button, menu) always asks first, in a card over the sidebar (Escape or Cancel keep it).
3. **Pinned** threads sit under a "Pinned" label at the top (a pinned thread is not listed twice); pinning is the store's `pinned` column, so the Tauri app shows the same pins. **Filter**: Ctrl+F or the filter button opens a box; every word must be in the title or the project name; matches ignore closed folders and the cap; Enter opens the first match; Escape closes it.
4. **Projects.** The add-folder button opens the system folder picker (`prompt_for_paths`) and makes a project named after the folder; double click or F2 on a header renames it; the menu has New thread, Copy path, Rename, Color (nine colours, remembered), Remove (asks). Dragging a thread row onto a header (any group with a folder, automatic repositories included) moves it (`Core::move_session`); the same through the menu.
5. **Footer.** Settings and Usage (toasts "arrive in Phase 7"), and the theme toggle (t3code light and dark; remembered). The title bar names the open thread; Ctrl+N and the new-thread buttons open a draft (nothing is stored until Phase 5's first message).
6. **Empty states.** `NoProjectsHero` (Add project, Start without a project) when there is no project and no thread; `NoActiveThreadState` when threads exist and none is open; a placeholder for an open thread or a draft until Phases 4 and 5.

### Core wiring
- `hermes-native.exe` takes `<data>/app.lock` (`hermes_core::AppLock`) before anything else; a second app on the folder shows "Hermes is already open..." in a message box (`rfd`, as the desktop app does) and exits 1. `--fixture` skips the lock and the core.
- Data folder: `theme::folder::data_dir()` = `HERMES_RS_HOME` else `%APPDATA%\hermes-rs` (the same as the runtime's).
- It starts its own tokio runtime (4 workers), opens the window at once, builds the core on GPUI's background executor (`RuntimeConfig::for_current_user`, `Core::new`, then `Core::start(true)`), and hands it to the model (`AppModel::connect`), which reads the list and follows `Core::subscribe()`. **`background = true`**: this app is the one app on the folder (the lock), exactly as the desktop app is; the scheduled curator belongs to it. Only the ACP agent, which runs beside another app, passes `false`.
- Views never call the core: `Sidebar` reads `AppModel` and calls `model.apply(Op)`; only `CoreBackend::run` turns an `Op` into core calls. Every backend call runs on the background executor; the list is changed first (optimistic) and re-read afterwards, a failure is a toast and the re-read restores it. `delete` and `move` are async in the core: `CoreBackend` uses the core's tokio handle with `block_on` from the background thread.
- **Toasts from core events** (`AppModel::on_event`): a failed turn (error toast, action "Open thread"), `QueuedFailed` (warning, "Open thread"), `CuratorFinished` (success or error), `ReviewFinished` with changes. Turn start and end, approvals and `Settled`, and title changes update the marks and the list. The toast action button opens the thread (new: `stack_elements` wires it).
- Where the extra data lives: **pins** in the store's `sessions.pinned` (already shared with the Tauri app); **project colours and closed folders** in `native-ui.json` (`sidebar_list`): presentation only, per UI, already written debounced off the UI thread and sanitised per part; a second side file would add nothing. Unread and failed marks are in memory for the run (t3code keeps `lastVisitedAt` per browser; a restart shows nothing unread).

### Review (Opus 5.5)
Reviewer: a fresh Opus 5.5 subagent, 2026-11-19. Main had not moved (no merge). The user's real data was not opened, copied or read; the real core was exercised on a synthetic folder (`target\native-test\seed`, seeded by the new ignored test `seed_synthetic_data_folder`: 3 projects, 50 threads, 6 pinned, 5 archived, 8 in no project, titles with emoji, a newline, 160 characters, untitled) and by a new test that goes through `AppModel` and a restart.

**Verdict: accepted after fixes.** The structure is sound (views read `AppModel` and send `Op`s; only `CoreBackend::run` calls the core; every backend call is on the background executor; no store schema change, pins are the existing `sessions.pinned` column written by `Store::set_pinned`).

Findings and fixes:
1. **Edits could land out of order** (bug). `AppModel::apply` spawned every `Op` at once on the background pool: two quick renames of one thread could reach the store in either order and the final re-read would show the wrong name. Now a queue: one edit at a time, in the user's order, a re-read when the queue is empty (`edits_reach_the_backend_one_at_a_time_in_the_users_order`, with a backend whose first edit is slow).
2. **An unreadable store looked like a first run** (bug, relevant to the user's database). `Core::sessions` turns a store error into an empty list, so the app showed "What should we work on?". `CoreBackend::snapshot` asks the store first and returns its error; when nothing was ever read the model goes to `Phase::Failed` and the main area says why; later failures stay a toast (`a_store_that_cannot_be_read_says_so_instead_of_an_empty_list`).
3. **No bounded shutdown** (hang risk). Dropping the tokio runtime after the event loop waits without end for blocking tasks (a curator or review in flight), leaving a windowless process holding `app.lock`. `app.rs` now calls `shutdown_timeout(2 s)`; the lock is released after it. A `--quit-after 8` run on the seeded folder exits 0.
4. **Titles with newlines/tabs** drew on two lines in a 36 px row: `ThreadItem::display_title` now joins them on one line (filter, toasts, title bar too).
5. **Focus after archive**: the keyboard cursor stayed on the archived row (the next arrow jumped to the top); it moves to the neighbour, as after a delete.
6. **`native-ui.json` growth**: a removed project's colour and closed state are dropped with it. Projects removed elsewhere (Tauri) still leave an entry: bounded by the user's own projects, left.
7. **Adding a folder that already is a project** created a duplicate project in the store; now the existing folder is opened and the cursor put on it (case and trailing separator ignored).
8. **Real core end to end**: new `edits_through_the_model_survive_a_restart` (AddProject, rename, pin, archive, delete, move through `AppModel` on a real core, then a second core on the same folder lists them; removing the project keeps its folder on disk and its thread). Test fixture: the `TestDir` fields of `Fx` moved last (ground rule 9). Dead code (`let _ = point(..)`, `menu_name`) removed.
